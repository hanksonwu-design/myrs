# Myrs 接 Supabase 設定指南

網頁版有兩種模式，看 `web/.env.local` 有沒有設定 Supabase 決定：

| | 示範模式（沒設定） | Supabase 模式（有設定） |
|---|---|---|
| 資料存哪裡 | 各自瀏覽器的 localStorage | Supabase 的 Postgres 資料庫，大家共用 |
| 登入 | 示範帳號一鍵登入、驗證碼固定 123456 | Email 或手機簡訊的一次性驗證碼 |
| 點數規則 | 在瀏覽器裡計算 | 在資料庫函式裡計算，使用者改不了 |
| 示範工具（切換帳號、快轉、重設） | 有 | 沒有 |

## 1. 建立專案

1. 到 <https://supabase.com> 註冊，按 **New project**。
2. 區域選 **Northeast Asia (Tokyo)**，離台灣最近。
3. 設一組資料庫密碼並記下來。免費方案就夠試點用。

## 2. 建立資料表和規則

到專案的 **SQL Editor**，依序貼上並執行這十一個檔案：

1. `migrations/20261119000001_schema.sql`：資料表、權限（RLS）、所有點數與交易規則。
2. `migrations/20261119000002_storage.sql`：照片儲存空間。刊登照片公開；聊天照片只有交易雙方看得到。
3. `migrations/20261119000003_cron.sql`：每 5 分鐘跑一次逾時取消、自動完成、食品過期。
   - 如果出現 pg_cron 的錯誤，先到 **Database → Extensions** 打開 `pg_cron`，再執行一次。
   - 跳過這一步也能用，網站開著時會自動補跑。
4. `migrations/20261119000004_review_fixes.sql`：上線前檢查後的修正。
   - 獎勵一人一份：同一個 Gmail 加 `+別名` 或加點，都算同一個人。
   - 接受後雙方都沒按「完成」，第 5 天提醒、第 7 天自動取消並退點。天數在後台「設定」調整，0 是不取消。
   - 交易有新進度時寄 Email 通知（要做第 7 節才會真的寄出）。
   - 管理員下架刊登、或有人刪除帳號時，爭議中的交易也會取消並退點。
5. `migrations/20261119000005_notify_cron.sql`：每分鐘檢查有沒有待寄的通知信。先做完第 7 節的 1～3 步再執行。
6. `migrations/20261119000006_improvements.sql`：第二輪檢查的修正和新功能。
   - 停權會員的刊登會隱藏、不能索取，還沒回覆的索取自動取消。
   - 封鎖對方時，兩人之間還沒開始的交易自動取消。
   - 刊登照片只能用 Myrs 上傳的網址。換了專案的話，先把檔案裡的 `photo_url_prefix` 網址改成自己的專案網址。
   - 刊登者在還沒接受任何索取前，可以修改面交地點。
   - 信任分數（完成交易數）、收藏、關鍵字通知（附近有符合的新刊登時寄信，每人每天最多 10 封）。
7. `migrations/20261120000007_admin_levels.sql`：管理團隊分層級，和停權原因、期限。
   - 三個層級：「擁有者」可以用所有後台功能，包括指派管理團隊、修改平台參數、調整點數；「管理員」可以審核刊登、處理檢舉與爭議、停權或恢復會員、設定商家；「審核員」只能審核刊登和處理檢舉（駁回或下架刊登）。
   - 原本的管理員會自動變成「擁有者」。至少要留一位擁有者；擁有者不能更改其他擁有者的權限。每次調整都會寫進後台紀錄，並寄信通知對方。
   - 停權要填原因，可以設定 1～365 天後自動恢復，或不設期限。停權和恢復都會寄信通知會員，會員登入時也會看到原因和恢復時間。
   - 管理團隊可以在刊登頁直接下架任何刊登，要填原因，刊登者會收到通知。
   - 管理團隊不能審核自己的刊登，也不能處理針對自己的檢舉。
   - 交易爭議的通知信只寄給管理員和擁有者。
8. `migrations/20261120000008_admin_tools.sql`：後台的禁售詞、全站公告和通知信狀況。
   - 擁有者可以在後台「設定」編輯禁售詞。新刊登包含這些字，會先進「刊登審核」；已上架的刊登不會重新檢查。
   - 擁有者可以發布全站公告，顯示在首頁最上方，可以設定結束時間。看過的人關掉後，要等下一則新公告才會再出現。
   - 管理員和擁有者可以在後台「通知信」看寄送狀況，寄失敗的信可以重寄。
   - 修改平台參數時，後台紀錄會寫出改了什麼，例如「手續費比例 10% → 8%」。
9. `migrations/20261120000009_wants.sql`：徵求貼文。
   - 會員可以發「徵求」，說明想要什麼和大概的位置（一樣模糊 60～180 公尺）。徵求會顯示 14 天，同時最多 3 則，每天最多發 5 則。
   - 別人可以發一則新刊登回應，或用自己已經上架的刊登回應。每人對同一則徵求最多回應 3 次。刊登上架時，發徵求的人會收到 Email 通知；先進審核的刊登，要等審核通過才會通知。
   - 徵求一樣檢查禁售詞，可以被檢舉（3 人檢舉會先隱藏），管理團隊可以在後台移除，並寄通知給發徵求的人。
   - 封鎖的雙方互相看不到對方的徵求；停權會員的徵求也不會公開。
10. `migrations/20261120000010_invites.sql`：邀請鄰居。
    - 每位會員有一組 6 碼邀請碼。從 Myrs 分享出去的刊登、徵求連結會帶著分享者的邀請碼。
    - 新會員加入 7 天內、完成第一筆交易前，可以填一次邀請碼。兩個人不能互相邀請。
    - 被邀請的人和「邀請人以外」的人完成第一筆交易後，雙方各得「邀請獎勵」點數（預設 20 點，擁有者可以在後台「設定」修改，設 0 就關閉）。這些點數算在每月獎勵上限內，也會跟其他獎勵一樣到期。
    - 同一個手機或 Email（包括 Email 別名）只能當一次「被邀請的人」拿獎勵，刪掉帳號重新註冊也一樣。
    - 邀請碼只有本人看得到；邀請紀錄只有雙方和管理員、擁有者看得到。
11. `migrations/20261120000011_impact.sql`：社區成果看板。
    - 首頁和「社區成果」頁顯示這個月和累計：分享了幾份食物、幾件衣物、幾位鄰居參與、幾件免費送出、幾則徵求找到了，還有最近六個月的長條圖。
    - 只算已完成的交易，一筆交易算一件。月份用台灣時間。
    - 這個函式只回傳總數，沒有名字、刊登或地點，所以沒登入的訪客也能看。這是 public 裡唯一開放給訪客呼叫的函式；之後的 migration 如果重寫權限區塊，要記得再加一次 `grant execute on function public.community_impact() to anon;`。
    - 會員自己的成果（「我的」頁面）在網頁上用自己的交易計算，不需要另外開權限。

用 Supabase CLI 的話，也可以在 `web/` 執行 `supabase link` 再執行 `supabase db push`。

## 3. 把金鑰填進網站

1. 到 **Project Settings → API** 複製 **Project URL** 和 **anon / publishable key**。
2. 把 `web/.env.example` 複製成 `web/.env.local`，填進去。
3. 重新啟動 `npm run dev`。

anon / publishable key 本來就會放在網頁裡，可以公開。**service_role / secret key 不要放進網站或 Git。**

## 4. 登入設定（Authentication）

**URL Configuration**

- **Site URL** 填正式網址，例如 GitHub Pages 的 `https://hanksonwu-design.github.io/myrs/`。
- **Redirect URLs** 加入正式網址的 `/login`（例如 `https://hanksonwu-design.github.io/myrs/login`）和開發用的 `http://localhost:3000/login`。

**Email 登入（預設就能用）**

- 到 **Emails** 的範本，在「Magic Link」和「Confirm signup」兩個範本裡加上 `{{ .Token }}`，信裡才會有驗證碼。現成的中文範本在 [email-templates.md](email-templates.md)。
  - 沒改範本也能登入：用同一個瀏覽器點信中的連結即可。
- Supabase 內建的寄信服務只會寄給專案成員（你自己），而且每小時只能寄幾封，只適合測試。要讓別人登入，請到 **SMTP Settings** 接自己的寄信服務：
  - **Gmail**（不用網域）：Host `smtp.gmail.com`、Port `465`、Username 和寄件信箱都填那個 Gmail、Password 填 Google 的「應用程式密碼」（要先開兩步驟驗證）。每天約可寄 500 封。
  - 有自己的網域時可以改用 Resend、SendGrid 等寄信服務。
  - 接好後到 **Rate Limits** 調高每小時可寄的信件數（試點設 100）。
- 驗證碼長度看 **Providers → Email → Email OTP length**（目前 8 位數）。登入頁收 6～8 位數都可以。

**手機簡訊登入（文件規劃的正式方式）**

1. 到 **Providers → Phone** 啟用，選簡訊商（Twilio、Vonage、MessageBird 等）並填入帳號。
2. 測試期可以在 **Test Phone Numbers and OTPs** 加入測試號碼，就不會真的寄簡訊。
   - 號碼不加 `+`，例如 `886912345678=123456`。
3. 在 `.env.local` 設定 `NEXT_PUBLIC_LOGIN_METHODS=phone,email`，登入頁就會出現「手機簡訊」分頁。

## 5. 設定第一位管理員

用自己的帳號在網站登入一次並完成註冊（取暱稱），然後在 SQL Editor 執行：

```sql
update public.profiles set role = 'admin'
where id = (select id from auth.users where email = 'you@example.com');
-- 用手機註冊的話改成：where phone = '886912345678'
```

重新整理網頁，右上角就會出現「後台」。用 SQL 設定的第一位管理員會自動成為「擁有者」。

之後要加人，不用再寫 SQL：請對方先註冊，再到後台「使用者」分頁搜尋他的名字，按「管理」→「管理權限」，選擇「審核員」、「管理員」或「擁有者」。試點商家也在同一個地方開通。

## 6. 測試規則

`npm run test:sql` 會在本機用 PGlite 跑一遍 schema，並檢查點數和權限規則，不需要連線到 Supabase。目前有 349 項檢查，例如：

- 凍結與退點。
- 手續費。
- 每月獎勵上限。
- 盲評。
- 檢舉 3 人自動隱藏。
- 封鎖。
- 逾時取消與自動完成。
- 一人一份獎勵（Email 別名）。
- 通知信的內容和收件人。
- 使用者不能直接改資料表。
- 停權、封鎖後自動取消交易。
- 收藏、關鍵字通知、修改面交地點。
- 管理團隊的層級權限、停權原因與自動恢復、最後一位擁有者不能被移除。
- 禁售詞、全站公告、通知信狀況與重寄、參數修改紀錄。
- 徵求的數量限制、回應、通知、檢舉與移除。
- 邀請碼的使用條件、邀請獎勵、Email 別名不能重複領、關閉邀請獎勵。
- 社區成果的件數、未完成和取消的交易不算、台灣時間的月份、徵求找到了、訪客只看得到總數。
- 點數守恆。

### 連線到真的 Supabase 測試

`npm run test:e2e` 會用三個臨時帳號，在真的 Supabase 專案上跑一遍：註冊、上傳照片、刊登、即時通知、交易、聊天照片、完成、盲評。

1. 先到 **Authentication → Sign In / Providers**，暫時打開 **Allow anonymous sign-ins**（允許匿名登入）。測試帳號都用匿名登入建立。
2. 執行 `npm run test:e2e`，最後一行出現 `all checks passed` 就是全部通過。
3. 測完到 **SQL Editor** 貼上並執行 [cleanup_e2e.sql](cleanup_e2e.sql)，刪掉所有測試帳號和它們的資料，最後一行顯示 `0` 就是清乾淨了。真實會員（用 Email 或手機登入的）不受影響。
4. **記得把 Allow anonymous sign-ins 關回去。** 網站本身不使用匿名登入，開著會讓別人不用驗證就能建立帳號。

## 7. Email 通知

交易有新進度時，系統會寄信通知當事人：有人索取、被接受、對方按了完成、快逾時、取消、完成、有人提出爭議（也會通知所有管理員）。自己按的動作不會寄給自己。

做法是資料庫把信放進 `notifications` 佇列，`send-notifications` 函式每分鐘用 Gmail 寄出。

1. 到 **Edge Functions → Deploy a new function → Via Editor**。
   - 名稱填 `send-notifications`。
   - 內容貼上 [functions/send-notifications/index.ts](functions/send-notifications/index.ts)。
   - 按 **Deploy function**。用 CLI 的話是 `supabase functions deploy send-notifications --no-verify-jwt`。
2. 部署後到函式的 **Settings**，關掉 **Verify JWT**，按 **Save changes**。
   - 排程呼叫時不帶金鑰，所以要關掉。
   - 這個函式不接受任何輸入，別人呼叫也只會讓佇列裡的信早一點寄出。
3. 到 **Edge Functions → Secrets** 新增 `SMTP_PASS`，填 Gmail 的應用程式密碼（和第 4 節 SMTP 用的同一組）。
   - 寄件信箱不是 `myrs.share@gmail.com` 的話，再加 `SMTP_USER`。
   - 網站網址不同的話，加 `SITE_URL`。
4. 執行第 2 節的 `migrations/20261119000005_notify_cron.sql`。換了專案的話，先把檔案裡的網址改成自己的專案網址。
5. 測試：在 SQL Editor 執行下面這行，1～2 分鐘內管理員信箱會收到信。

```sql
select private.notify((select id from public.profiles where role = 'admin' limit 1), '測試通知', '這是一封 Myrs 通知測試信。', '/');
```

沒收到的話，看寄送紀錄：

```sql
select created_at, subject, attempts, sent_at, last_error from public.notifications order by created_at desc limit 10;
```

- `last_error` 會寫錯誤原因，例如密碼錯誤。同一封信最多試 5 次。
- Gmail 每天約可寄 500 封，和登入驗證信共用額度。
- 也可以在後台的「通知信」分頁看：等待寄出、寄送失敗、24 小時內寄出的數量，和每封信的錯誤原因。寄失敗的信按「重寄」會再試 5 次。有信排隊超過 15 分鐘還沒寄出，表示寄信程式可能停了，請檢查上面 1～3 步。

## 安全設計重點

- 瀏覽器只能「讀」資料表，而且只讀得到自己有權限的列（RLS）。所有寫入都要透過資料庫函式，點數規則在伺服器端執行。
- 點數沒有存「餘額」欄位，餘額一律等於帳本（ledger）加總，方便對帳。
- 公開的刊登只有模糊後的位置（偏移 60～180 公尺）。精確地點存在 `listing_secrets`，只有刊登者、管理員、和被接受的索取者讀得到（索取被取消後就看不到了）。
- 「審核員」只看得到審核需要的資料（待審核的刊登和檢舉），看不到別人的點數、聊天內容、精確面交地點、停權紀錄和後台紀錄。這些只有「管理員」和「擁有者」看得到。
- 發布時的地點搜尋用 OpenStreetMap 的 Nominatim（免費、不用金鑰）。依它的使用規定，只在按「搜尋」時查詢、每秒最多一次；自動帶入的地點名稱不會包含門牌號碼。
- 手機號碼和 Email 只存在 Supabase Auth，不會出現在任何公開資料表。
- 後台「通知信」只顯示主旨、收件會員的名稱和寄送狀態。Email 地址和信件內容不會傳到瀏覽器，錯誤訊息裡的 Email 也會遮掉。
- 評價是盲評：雙方都評完，或完成滿 7 天，才會公開。
- 刪除帳號會取消進行中的交易、下架刊登、移除登入資料，只留下「已刪除的使用者」的空殼，讓舊交易紀錄還能顯示。同一個手機或 Email 重新註冊，不會再拿一次新手點數。

## 目前的限制

- 獎勵點數的到期日只記錄、會顯示，還不會真的扣除。要扣除得做先進先出的點數消耗，留到營收版。
- 網頁一次載入使用者看得到的所有資料，大約幾千筆以內都沒問題。超過的話，要改成分頁和伺服器端統計（例如後台儀表板）。
- 通知只寄 Email，沒有手機推播，使用者也還不能關掉交易通知信（關鍵字通知可以在「我的」頁面刪除）。
- 關鍵字通知只比對刊登的標題、說明和細項文字，不會比對照片。
- 分享到 LINE 時，預覽只會顯示 Myrs 的網站名稱，不會顯示物品照片。網站放在 GitHub Pages，沒辦法替每則刊登產生各自的預覽圖。
- 管理員在後台看不到使用者的手機號碼。需要客服查詢時，到 Supabase 的 **Authentication → Users** 查。
